# neoagent v3.2b Code Review

日期: 2026-04-12  
审查对象: neoagent v3.2b Multi-Agent 实现  
权威参考: `docs/superpowers/specs/2026-04-12-neoagent-v3.2b-design.md`

## 审查范围

本次 review 覆盖以下内容：

- `neoagent/multi/` 全部实现
- `neoagent/events.py`
- `neoagent/config.py`
- `neoagent/agent.py`
- `tests/multi/` 全部测试

重点审查维度：

- Spec 合规性
- 架构质量
- 安全性
- 代码质量
- 测试质量

## 执行摘要

v3.2b 的整体方向是对的：`Orchestrator + Workers` 的组合关系清晰，`WorkerCard -> NeoAgent` 的复用也基本符合 spec 的大方向。事件冒泡放在 Python 回调层而不是 LLM 上下文里，这个设计决策也正确。

但当前实现仍然存在几个结构性问题，最核心的是：

1. 真实 Worker 任务没有被注册成可取消的 `asyncio.Task`
2. 超时语义被错误归类为 `failed`，不是 spec 要求的 `cancelled`
3. `Task` 协议对象与 spec 漂移较大，关键约束没有真正透传到运行时
4. “并行执行”在真实 `delegate_task` 路径上并没有完全落地
5. 测试对关键运行路径 mock 过多，而且在当前环境下无法通过收集阶段

这意味着当前版本在“接口形状”上已经接近 spec，但在“真实运行语义”上还没有达到 spec 所描述的完成度。

## 严重问题（必须修复）

### 1. 真实 Worker 没有注册为可取消的 asyncio.Task

- **问题描述**
  `spawn_worker` 和 `delegate_task` 都是在 tool 内直接 `await _run_worker(...)`。`TaskTracker.set_asyncio_task()` 没有接入真实提交路径，导致 `cancel_task`、`list_tasks`、`Orchestrator.close()` 无法控制真实运行中的 Worker。
- **文件和行号**
  - `neoagent/multi/tools/spawn_worker.py:129`
  - `neoagent/multi/tools/delegate_task.py:148`
  - `neoagent/multi/task.py:124`
  - `neoagent/multi/orchestrator.py:107`
- **风险**
  取消语义在真实场景下基本失效。接口看起来支持取消，但运行时并没有把 Worker 变成可管理的后台任务。
- **修复建议**
  增加统一的任务提交层，例如 `TaskManager.submit(...) -> task_id`。内部用 `asyncio.create_task()` 包装 `_run_worker()`，创建后立刻调用 `set_asyncio_task()`，并登记 `worker_name/depth/created_at` 等运行时元数据。tool 层只负责 submit / await / cancel，不直接执行 Worker。

### 2. 超时被错误归类为 failed，不是 cancelled

- **问题描述**
  `asyncio.timeout()` 在 Python 3.12 抛出的是 `TimeoutError`，当前 `_run_worker()` 只单独捕获了 `asyncio.CancelledError`，所以超时最终会落入通用异常分支，返回 `TaskResult(status="failed")`。
- **文件和行号**
  - `neoagent/multi/task.py:307`
  - `neoagent/multi/task.py:340`
  - `neoagent/multi/task.py:351`
- **风险**
  直接违背 spec 第 10.1 节和第 8 节的取消语义。上层编排会把超时误认为普通失败，导致错误决策。
- **修复建议**
  显式捕获 `TimeoutError`，并映射为 `status="cancelled"`。如果要区分来源，可以在 `error` 或 `metadata` 中标记 `reason="timeout"`，但最终状态应与 spec 保持一致。

### 3. 取消时没有真正生成 work_summary

- **问题描述**
  spec 明确要求取消时通过程序化方式提取 `work_summary`。当前实现虽然写了 `_extract_work_summary()`，但取消分支并未调用，只返回固定字符串 `（任务被取消）`。
- **文件和行号**
  - `neoagent/multi/task.py:216`
  - `neoagent/multi/task.py:340`
- **风险**
  取消后的中间工作信息丢失，Orchestrator 无法根据部分进展做后续决策。
- **修复建议**
  在取消和超时路径上从真实会话消息中提取摘要，并返回 `turns_completed` 的真实值，而不是固定 `0`。

### 4. Task Envelope 与 spec 漂移，关键约束未真正透传

- **问题描述**
  spec 中 `Task` 是 `instruction + context + constraints + metadata + max_output_tokens`。当前实现改成了 `context: tuple[str, ...] + max_turns + timeout + max_output_tokens + metadata`，而且 `_run_worker()` 只用到了 `timeout` 和输出截断，`max_turns/max_tokens/metadata` 都没有真正进入运行时执行路径。
- **文件和行号**
  - `neoagent/multi/task.py:31`
  - `neoagent/multi/task.py:292`
  - `neoagent/multi/task.py:307`
  - `neoagent/agent.py:119`
- **风险**
  任务协议不稳定，后续 v3.2c Channel 和远期 A2A 很难复用。更严重的是，任务级的限制并没有真正生效。
- **修复建议**
  回到 transport-safe 的稳定 envelope 设计。优先保留 `context: tuple[Message, ...]` 和 `constraints`，不要在 tool 层手工做 JSON 字符串编码。然后扩展 `NeoAgent.run` / `QueryLoop` 支持 per-task `max_turns/max_tokens`。

## 重要问题（建议修复）

### 5. delegate_task 在真实 QueryLoop 中并不天然并行

- **问题描述**
  `DelegateTaskTool` 没有标记 `is_concurrent_safe = True`，而 `ToolExecutor` 只会并行执行并发安全工具。因此在同一轮模型生成多个 `delegate_task` 调用时，它们会被串行执行。
- **文件和行号**
  - `neoagent/multi/tools/delegate_task.py:81`
  - `neoagent/tools/base.py:12`
  - `neoagent/tools/executor.py:57`
- **风险**
  spec 的“并行 worker 执行”在静态 worker 路径上没有完全实现，吞吐会明显低于预期。
- **修复建议**
  在修复后台任务提交模型后，把 `delegate_task` 也做成真正的并发安全提交操作，或者显式提供批量委派接口。

### 6. list_tasks 想显示 worker_name，但 TaskTracker 根本不保存

- **问题描述**
  `ListTasksTool` 试图从 `TaskTracker.list_all()` 的结果里读取 `worker_name`，但当前 `TaskTracker` 实际只保存 `task_id/instruction/status`，因此真实输出会一直是 `?`。
- **文件和行号**
  - `neoagent/multi/task.py:162`
  - `neoagent/multi/tools/list_tools.py:72`
- **风险**
  任务观测性不足，用户很难知道某个 task_id 属于哪个 worker，也会削弱 `cancel_task` 的可操作性。
- **修复建议**
  在 tracker 中保存 task runtime metadata，至少包含 `worker_name/depth/status/created_at`。

### 7. multi 模块在干净环境下无法导入

- **问题描述**
  `neoagent.multi.__init__` 会立即导入 `parser.py`，而 `parser.py` 依赖 `yaml`。但项目依赖中没有声明 `PyYAML`。因此 `pytest -q tests/multi` 在收集阶段就失败。
- **文件和行号**
  - `neoagent/multi/__init__.py:1`
  - `neoagent/multi/parser.py:5`
  - `pyproject.toml:10`
- **风险**
  当前 multi 能力在最基本的环境安装层面都不完整，CI 或新环境导入会直接失败。
- **修复建议**
  把 `PyYAML` 加入项目依赖。额外建议把 `neoagent.multi.__init__` 改成更窄或惰性的导出，避免 parser 依赖污染所有子模块导入。

### 8. Worker 复用的是同一份 tool 实例，不是真正隔离

- **问题描述**
  `_create_worker_agent()` 直接把 orchestrator `_tool_pool` 中的工具实例注册到 worker agent。也就是说多个 worker 共享同一个 tool 对象。
- **文件和行号**
  - `neoagent/multi/worker.py:114`
- **风险**
  如果工具带有实例状态，多个 worker 并发时会发生状态串扰或竞态。这与“每个 worker 是独立 NeoAgent 实例”的隔离语义不一致。
- **修复建议**
  工具池应保存 tool factory 或 blueprint，创建 worker 时生成 agent-local 工具实例。

### 9. 集成测试对关键运行路径 mock 过多

- **问题描述**
  多个所谓 integration test 实际上 mock 了 `_create_worker_agent()` 或直接 mock 掉 `worker.run()`，没有跑真实的 `ToolExecutor -> TaskTracker -> _run_worker -> EventBus` 协作路径。
- **文件和行号**
  - `tests/multi/test_integration.py:89`
  - `tests/multi/test_integration.py:205`
  - `tests/multi/tools/test_delegate_task.py:52`
  - `tests/multi/tools/test_spawn_worker.py:63`
- **风险**
  取消链路、超时语义、真实并行、task 登记等关键 bug 很容易漏测。
- **修复建议**
  用 fake provider 跑真实路径，减少对 `_create_worker_agent()` / `_run_worker()` 的 patch，重点补端到端行为测试。

## 次要问题（可选修复）

### 10. frozen dataclass 只做到了浅不可变

- **问题描述**
  `Task` 是 frozen dataclass，但 `metadata` 仍然是可变 `dict`。`TaskResult` 的 `usage/work_summary` 注解也和运行时值不完全一致。
- **文件和行号**
  - `neoagent/multi/task.py:41`
  - `neoagent/multi/task.py:73`
- **风险**
  类型和不可变性承诺不一致，后续维护成本上升。
- **修复建议**
  `metadata` 改为不可变映射；`usage/work_summary` 类型改为显式可选。

### 11. 事件发射 helper 重复实现

- **问题描述**
  `_emit_dispatch_event()` 和 `_emit_complete_event()` 在 `spawn_worker.py` 和 `delegate_task.py` 中各复制了一份。
- **文件和行号**
  - `neoagent/multi/tools/spawn_worker.py:22`
  - `neoagent/multi/tools/delegate_task.py:22`
- **风险**
  事件结构演进时容易出现双边漂移。
- **修复建议**
  提取到共享 helper 模块。

### 12. task_id 生成策略不一致

- **问题描述**
  `Task.create()` 用完整 UUID，而 tool 层又自己手工生成截断版 8 位 ID。
- **文件和行号**
  - `neoagent/multi/tools/spawn_worker.py:112`
  - `neoagent/multi/tools/delegate_task.py:120`
  - `neoagent/multi/task.py:55`
- **风险**
  约定不统一，也引入不必要的碰撞概率。
- **修复建议**
  统一使用完整 UUID。

## 亮点

- `Orchestrator` 采用组合 `NeoAgent`，而不是继承或侵入现有 agent 结构，这个方向是对的。
- `WorkerCard.instruction -> system_prompt` 的接线简单直接，复用了现有 PromptBuilder 体系。
- `WorkerCard.tools` 的显式授权模型清晰，权限边界容易理解。
- 事件冒泡放在 Python 回调层，不进入 LLM 上下文，这是合理且克制的设计。
- `WorkerPool` / `TaskTracker` / tool 层拆分基本符合单一职责，后续继续抽象是有基础的。

## v3.3 架构建议

### 1. 先补 WorkerProtocol，而不是继续堆 tool 逻辑

建议尽快引入明确的 Worker 运行协议，例如：

```python
class WorkerProtocol(Protocol):
    async def submit(self, task: Task) -> str: ...
    async def get_result(self, task_id: str) -> TaskResult | None: ...
    async def cancel(self, task_id: str) -> bool: ...
```

这样本地 NeoAgent Worker、未来的 Channel Worker、远期的 A2AWorker 才能共享同一套调度语义。

### 2. 引入 TaskHandle / RuntimeRecord

目前 `TaskTracker` 只像一个“轻量字典”。v3.3 应升级为真正的 runtime store，统一管理：

- `task_id`
- `worker_name`
- `depth`
- `asyncio_task`
- `created_at`
- `status`
- `result`

这样 `cancel_task`、`list_tasks`、`close()`、事件发射和后续 Channel 抽象都能围绕同一个事实源工作。

### 3. 为 v3.2c Channel 做 InprocChannel 抽象

如果 v3.2c 计划做 Channel，建议先定义最小的本地进程内版本：

- `InprocChannel`
- `LocalWorkerRuntime`

然后把现在直接调用 `_run_worker()` 的路径改为“通过 channel 提交任务”。这样未来接远程 A2A 只需新增传输实现，不需要再改 Orchestrator 调度逻辑。

### 4. 工具池改成 factory，而不是实例池

未来一旦 worker 数量上来，或者工具开始持有状态，共享实例会成为隐患。v3.3 应把 `_tool_pool` 从 `dict[str, BaseTool]` 升级为：

- `dict[str, ToolFactory]`

worker 初始化时生成自己的局部工具实例，真正做到“独立 worker、最小权限、最小共享”。

### 5. 测试策略需要从“接口测试”升级到“语义测试”

建议 v3.3 补三类端到端测试：

- 真实超时 -> `cancelled`
- 真实 cancel_task -> Worker 被取消并有 `work_summary`
- 真实多 Worker 并行 -> Semaphore 限流 + 单个失败不影响其他任务

这三类测试是当前实现最缺、但也是最能证明 multi-agent 基础设施真正可用的部分。

## 测试结论

本次尝试执行：

```bash
pytest -q tests/multi
```

结果在测试收集阶段失败，错误为：

```text
ModuleNotFoundError: No module named 'yaml'
```

根因：

- `neoagent.multi.__init__` 导入了 `parser.py`
- `parser.py` 依赖 `yaml`
- `pyproject.toml` 未声明 `PyYAML`

因此当前无法基于本地环境确认 `tests/multi` 的真实通过率。这个问题本身也应视为 v3.2b 的发布阻断项之一。

## 结论

当前 v3.2b 可以认为已经完成了 Multi-Agent 架构雏形，但还没有达到“运行语义闭环”的程度。最优先的修复顺序建议如下：

1. 修复依赖与导入问题，保证 `tests/multi` 能运行
2. 重构任务提交路径，真正接通 `TaskTracker.set_asyncio_task()`
3. 修正 timeout / cancel / work_summary 语义
4. 把 task runtime metadata 统一收口到 tracker
5. 补真实端到端测试，再考虑 v3.2c Channel 抽象

如果以上问题修完，v3.2b 才能作为 v3.2c Channel 和远期 A2A 的稳定基座。
